SICMA: cómo consumir la API del backend

Endpoints, autenticación, reglas para mostrar los datos del sensor y cómo conectarse al backend desde otra red. Todo lo que no está implementado aparece marcado como tal.

Backend Django 6.1 · DRF 3.18 · SimpleJWT 5.5 Base de datos MySQL 8 (InnoDB Cluster) Sensor ESP32-S3 + DHT22 · 60 s Revisado 24-09-2026 · rama main
Implementado existe en el código Propuesta contrato acordado, falta programarlo Por confirmar decisión pendiente

Qué existe hoy

El backend tiene dos apps: login (autenticación y recuperación de contraseña) y mediciones (recepción de lecturas del sensor). Todas las rutas cuelgan de /api/.

MétodoRutaAccesoPara qué sirve
POST/api/auth/token/PúblicoIniciar sesión: devuelve access y refresh
POST/api/auth/token/refresh/PúblicoObtener un access nuevo
GET/api/auth/me/JWTComprobar la sesión (hoy solo devuelve el username)
POST/api/auth/password-reset/PúblicoPedir el correo de recuperación
POST/api/auth/password-reset/confirm/PúblicoGuardar la nueva contraseña
POST/api/mediciones/DispositivoLo usa el ESP32. El frontend no lo llama.

Todavía no hay endpoints de lectura. Con la API actual el frontend puede construir el login, la recuperación de contraseña y el control de sesión. Para el dashboard, el detalle y el historial, este documento define un contrato propuesto: puedes maquetar con datos simulados que sigan esa forma exacta y conectarlos cuando el backend los publique.

Cómo llegan los datos

SensorESP32-S3 + DHT22 mide temperatura y humedad
Envío · cada 60 sPOST /api/mediciones/ con X-Device-Key
BackendDjango valida, descarta duplicados y guarda
Base de datosMySQL en InnoDB Cluster
LecturaAngular (web) e Ionic (móvil) con GET + JWT

El frontend solo lee a través de la API de Django: nunca habla con el sensor ni con la base de datos.

El header X-Device-Key es exclusivo del dispositivo y no debe aparecer en ningún archivo del código Angular o Ionic.

Autenticación y perfiles

El frontend usa el JWT de usuario (SimpleJWT). No hay sesiones ni cookies, así que tampoco hace falta token CSRF.

1 · LoginPOST usuario y contraseña a /auth/token/
2 · Guardaraccess y refresh
3 · LlamarHeader Authorization: Bearer <access>
4 · RenovarSi responde 401, POST del refresh y repetir
5 · SalirBorrar los tokens. No hay endpoint de logout.

Lo acordado frente a lo que hay hoy

TemaAcordadoHoy en el código
Rol del usuarioClaim rol dentro del tokenNo existe El token solo trae user_id, exp, iat, jti y token_type. El login usa auth_user; el rol está en otra tabla (usuario) sin enlazar.
Expiración15 min de inactividadNo existe Configuración por defecto: access de 5 min, refresh de 24 h, sin rotación.
Campo de login—Hecho username de Django, no el correo.

Cuando el backend agregue el claim, el payload del access se verá así (se lee decodificando la parte central del JWT en base64url; no hace falta ninguna librería):

{ "token_type": "access", "exp": 1790265600, "user_id": 14, "rol": "Jefatura", "jti": "…" }

Usa el rol solo para mostrar u ocultar opciones. Los permisos reales los aplica el backend en cada endpoint.

Inactividad de 15 minutos

El polling no cuenta como actividad. El dashboard llama a la API cada 60 s; si cada 401 se renueva el token automáticamente, la sesión no vencería nunca. Por eso la inactividad se mide en el frontend:

  • Guarda la hora de la última interacción real (click, keydown, touchstart, cambio de ruta).
  • Antes de renovar el token, comprueba esa hora. Si pasaron más de 15 min, cierra la sesión y ve al login en vez de renovar.
  • En el backend, el access durará 15 min (SIMPLE_JWT). Así, si alguien copia un token, sirve como máximo 15 min.

Entorno de desarrollo

Desarrollo desde otra red

El backend corre en un PC de la red del equipo y la base de datos está en 192.168.100.95, una IP privada. Desde otra casa o red, http://192.168.100.102:8000 no responde, y el backend tampoco se puede correr en tu equipo porque no alcanza la base de datos.

Hay tres formas de trabajar. Tu IP o tu red no importan: lo que cambia es cómo llegas al backend.

OpciónQué hace el backendQué hace el frontendHTTPSCelular
A · Tailscale
Recomendada		 Instala Tailscale en el PC del backend y te invita a la red (tailnet). Ejecuta tailscale serve --bg 8000 para publicar Django en https://pc-sicma.<tailnet>.ts.net. Instala Tailscale, acepta la invitación y usa esa URL como apiUrl. Sí, con certificado válido Instala la app Tailscale en el celular con la misma cuenta

C · Datos simulados Nada. Trabaja con JSON de ejemplo que sigan el contrato y activa useMock en environment.ts. — —
  • Opción A: el backend queda accesible solo para quienes están en la tailnet, no en internet. Para usar tailscale serve hay que activar HTTPS una vez en la consola de administración de Tailscale.
  • Opción B: expone el backend a internet con DEBUG = True, que muestra trazas de error detalladas. Úsala solo mientras pruebas y cierra el túnel al terminar.
  • Para A o B, el backend debe: correr con python manage.py runserver 0.0.0.0:8000, agregar el nombre público a ALLOWED_HOSTS (si no, responde 400 Bad Request) y configurar CORS (siguiente sección).
  • Combina C con A o B: avanza con datos simulados y conéctate al backend real para probar la integración.

CORS y orígenes

CORS compara el origen del frontend (esquema + host + puerto de la página), no la IP del desarrollador. Mientras trabajes con ng serve o ionic serve en tu equipo, tu origen es localhost desde cualquier red, así que la lista es fija:

OrigenDe dónde viene
http://localhost:4200ng serve (Angular web)
http://localhost:8100ionic serve (Ionic en el navegador)
https://localhostApp Capacitor en Android (esquema por defecto desde Capacitor 6)
http://localhostApp Capacitor en Android con androidScheme: 'http' (ver siguiente sección)
capacitor://localhostApp Capacitor en iOS

Configuración que debe agregar el backend (django-cors-headers ya está instalado, pero no activado):

# backendsicma/settings.py
INSTALLED_APPS += ['corsheaders']
MIDDLEWARE.insert(0, 'corsheaders.middleware.CorsMiddleware')   # debe ir primero

CORS_ALLOWED_ORIGINS = [
    'http://localhost:4200', 'http://localhost:8100',
    'http://localhost', 'https://localhost', 'capacitor://localhost',
]

ALLOWED_HOSTS = ['localhost', '127.0.0.1', '192.168.100.102',
                 'pc-sicma.<tailnet>.ts.net',   # opción A
                 '.trycloudflare.com']           # opción B (solo desarrollo)

Si abres la web desde el navegador del celular con ng serve --host 0.0.0.0, el origen pasa a ser http://<tu-ip>:4200 y habría que agregarlo a la lista. Para probar en el celular es más simple usar la app Capacitor.

Para la web también puedes saltarte CORS con el proxy de Angular: proxy.conf.json con {"/api": {"target": "https://pc-sicma.<tailnet>.ts.net", "secure": true, "changeOrigin": true}} y apiUrl: '/api'.

Android, HTTP y HTTPS

Con las opciones A o B la API ya va por HTTPS y no hace falta nada especial en Android. Esta sección aplica solo si pruebas contra http://, por ejemplo con la IP de la red local cuando estás en la oficina.

En ese caso chocan dos bloqueos:

  • Tráfico sin cifrar: Android bloquea http:// por defecto. Habilítalo solo en la build de desarrollo con un manifiesto de debug, así nunca llega a producción:
<!-- android/app/src/debug/AndroidManifest.xml (solo se usa en builds debug) -->
<manifest xmlns:android="http://schemas.android.com/apk/res/android"
          xmlns:tools="http://schemas.android.com/tools">
  <application android:usesCleartextTraffic="true"
               tools:replace="android:usesCleartextTraffic" />
</manifest>
  • Contenido mixto: desde Capacitor 6 la app se sirve desde https://localhost, y el WebView bloquea llamadas de una página HTTPS a una API HTTP. En desarrollo, cambia el esquema:
// capacitor.config.ts (solo desarrollo; no dejarlo en la build de producción)
server: { androidScheme: 'http' }

En producción todo va por HTTPS: sin usesCleartextTraffic, con androidScheme por defecto, DEBUG = False y CORS_ALLOWED_ORIGINS solo con los orígenes reales.

environment.ts

La URL base va en los archivos de entorno de Angular, nunca escrita dentro de los servicios. Con Tailscale o Cloudflare usa el nombre público, no localhost ni una IP 192.168.x.x: el celular o tu equipo en otra red no la alcanzan.

// src/environments/environment.development.ts
export const environment = {
  production: false,
  apiUrl: 'https://pc-sicma.<tailnet>.ts.net/api',   // o la URL de trycloudflare, o '/api' con proxy
  pollMs: 60_000,
  idleLogoutMs: 15 * 60_000,
  useMock: false,
};

// src/environments/environment.ts (producción)

  production: true,
  apiUrl: 'https://sicma.<dominio>/api',

  useMock: false,

A 60 s por lectura, cada sensor genera 1.440 mediciones al día y unas 10.000 por semana.

Decimales: string a número

DRF envía los DecimalField como texto ("24.50") para no perder precisión (COERCE_DECIMAL_TO_STRING = True por defecto). Conviértelos al recibirlos, en un solo lugar:

const num = (v: string | number | null): number | null => (v === null ? null : Number(v));

Si el backend cambia COERCE_DECIMAL_TO_STRING a False, llegarán como números y esta función sigue funcionando.

Fechas y zona horaria

  • La API entrega todas las fechas en UTC, ISO 8601 (2026-09-24T14:05:00Z).
  • Conviértelas a hora de Chile solo al mostrarlas, con la zona America/Santiago. No uses -03:00 fijo: Chile pasa a UTC−4 en invierno.
  • DatePipe de Angular convierte a la zona del equipo del usuario y solo acepta desfases ('-0300'), no nombres IANA. Para forzar la hora de Chile, usa Intl.DateTimeFormat:
// hora-chile.pipe.ts
const fmt = new Intl.DateTimeFormat('es-CL', {
  timeZone: 'America/Santiago',
  day: '2-digit', month: '2-digit', year: 'numeric',
  hour: '2-digit', minute: '2-digit', second: '2-digit', hourCycle: 'h23',
});

@Pipe({ name: 'horaChile', standalone: true })
export class HoraChilePipe implements PipeTransform {
  transform(iso: string | null): string { return iso ? fmt.format(new Date(iso)) : '—'; }
}
// {{ m.fecha_hora_medicion | horaChile }}  →  24-09-2026, 11:05:00

Para filtrar (desde/hasta), envía a la API instantes UTC con date.toISOString(). Un rango “últimas 24 h” es new Date(Date.now() - 24*3600e3).toISOString(), sin cálculos de zona.

Particularidades de la serie

Las mediciones pueden llegar atrasadas y en ráfaga

Si el ESP32 pierde la conexión, guarda las lecturas en cola y las envía al reconectarse con su hora original. En las pruebas llegaron 6 mediciones de 5 minutos distintos en el mismo segundo:

  • Gráficos e historial: ordena siempre por fecha_hora_medicion, nunca por id ni por recepción.
  • Traer lo nuevo: filtra por fecha_hora_recepcion (o por id). Si filtras por hora de medición, las lecturas atrasadas quedan fuera porque su hora es anterior a la última que ya tienes.
  • Duplicados: al combinar datos nuevos con los que ya tienes, usa evento_id como clave.

Huecos: no unir lo que no se midió

Si el sensor estuvo apagado, la serie queda con huecos. Si el gráfico une dos puntos separados por más de 3 intervalos (180 s), dibuja una tendencia que no existe. Inserta un punto nulo en cada hueco y desactiva la unión de nulos en la librería (spanGaps: false en Chart.js, connectNulls: false en ECharts):

interface Punto { t: number; temp: number | null; hum: number | null }

export function serieConHuecos(ms: Medicion[], intervaloSeg: number, factor = 3): Punto[] {
  const limite = factor * intervaloSeg * 1000;
  const orden = [...ms].sort((a, b) =>
    Date.parse(a.fecha_hora_medicion) - Date.parse(b.fecha_hora_medicion));
  const out: Punto[] = [];
  let prev: number | null = null;
  for (const m of orden) {
    const t = Date.parse(m.fecha_hora_medicion);
    if (prev !== null && t - prev > limite) out.push({ t: prev + intervaloSeg * 1000, temp: null, hum: null });
    out.push({ t, temp: num(m.temperatura), hum: num(m.humedad) });
    prev = t;
  }
  return out;
}

Estado del sensor: en línea o sin datos

No hay una señal de “sigo vivo” aparte: el estado se calcula con la última medición. Si la última fecha_hora_medicion tiene más de 3 × intervalo de antigüedad (180 s con el intervalo actual), el sensor se muestra como sin datos.

export function enLinea(ultima: string | null, intervaloSeg: number, ahora = Date.now()): boolean {
  return ultima !== null && ahora - Date.parse(ultima) <= 3 * intervaloSeg * 1000;
}
sensor.estadoÚltima lecturaMostrar
ActivoHace ≤ 3 × intervaloEn línea
ActivoMás antigua, o no haySin datos con la hora de la última lectura
InactivoCualquieraInactivo (dado de baja; no es una falla)

Este cálculo usa el reloj del equipo del usuario. Si ese reloj está desfasado, el estado puede fallar. Si ocurre, el backend puede calcular en_linea y entregarlo en la respuesta.

Actualización en pantalla

Basta con consultar la API cada 60 s, el mismo intervalo del sensor. El prototipo no necesita WebSockets.

// Dashboard: una llamada trae los sensores con su última medición
sensores$ = timer(0, environment.pollMs).pipe(
  switchMap(() => this.api.sensores()),
  shareReplay({ bufferSize: 1, refCount: true }),
);

// Detalle: carga el rango y luego pide solo lo recibido después de lo último que tienes
private ultimaRecepcion = '';
private porEvento = new Map<string, Medicion>();

refrescar(sensorId: number) {
  return this.api.mediciones({ sensor: sensorId, recibido_desde: this.ultimaRecepcion }).pipe(
    map(page => {
      for (const m of page.results) {
        this.porEvento.set(m.evento_id, m);
        if (m.fecha_hora_recepcion > this.ultimaRecepcion) this.ultimaRecepcion = m.fecha_hora_recepcion;
      }
      return serieConHuecos([...this.porEvento.values()], this.intervaloSeg);
    }),
  );
}
  • Las fechas ISO en UTC con el mismo formato se pueden comparar como texto; por eso funciona > entre strings.
  • Detén el polling cuando la vista no esté visible (takeUntilDestroyed; en Ionic, ionViewWillLeave) y cuando la app pase a segundo plano.
  • Recuerda que el polling no cuenta como actividad del usuario (ver inactividad).

Cliente Angular

Interceptor funcional (Angular 17+) que agrega el token, lo renueva una sola vez ante un 401 y cierra la sesión si el usuario lleva más de 15 minutos sin interactuar. La renovación se comparte, así varias llamadas simultáneas del polling no piden varios tokens a la vez.

// auth.service.ts
@Injectable({ providedIn: 'root' })
export class AuthService {
  private http = inject(HttpClient);
  private router = inject(Router);
  private access: string | null = null;
  private renovando$: Observable<string> | null = null;
  private ultimaActividad = Date.now();

  constructor() {
    for (const ev of ['click', 'keydown', 'touchstart'])
      window.addEventListener(ev, () => (this.ultimaActividad = Date.now()), { passive: true });
  }

  get token() { return this.access; }
  get rol(): string | null {                        // cuando el backend agregue el claim
    if (!this.access) return null;
    const payload = this.access.split('.')[1].replace(/-/g, '+').replace(/_/g, '/');
    return JSON.parse(atob(payload)).rol ?? null;
  }

  login(username: string, password: string) {
    return this.http.post<{ access: string; refresh: string }>(
      `${environment.apiUrl}/auth/token/`, { username, password },
    ).pipe(tap(t => { this.access = t.access; localStorage.setItem('sicma_refresh', t.refresh); }));
  }

  renovar(): Observable<string> {
    const refresh = localStorage.getItem('sicma_refresh');
    const inactivo = Date.now() - this.ultimaActividad > environment.idleLogoutMs;
    if (!refresh || inactivo) { this.logout(); return throwError(() => new Error('sesion')); }
    this.renovando$ ??= this.http.post<{ access: string }>(
      `${environment.apiUrl}/auth/token/refresh/`, { refresh },
    ).pipe(
      map(r => (this.access = r.access)),
      finalize(() => (this.renovando$ = null)),
      shareReplay(1),
    );
    return this.renovando$;
  }

  logout() {
    this.access = null;
    localStorage.removeItem('sicma_refresh');
    this.router.navigateByUrl('/login');
  }
}

// auth.interceptor.ts
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService);
  if (!req.url.startsWith(environment.apiUrl) || req.url.includes('/auth/')) return next(req);

  const conToken = (t: string | null) =>
    t ? req.clone({ setHeaders: { Authorization: `Bearer ${t}` } }) : req;

  return next(conToken(auth.token)).pipe(
    catchError((err: HttpErrorResponse) =>
      err.status === 401
        ? auth.renovar().pipe(switchMap(t => next(conToken(t))))
        : throwError(() => err)),
  );
};

// app.config.ts
provideHttpClient(withInterceptors([authInterceptor]))

Al abrir la app sin access en memoria pero con refresh guardado, la primera llamada devolverá 401 y el interceptor renovará el token solo. Si la renovación falla, manda al login.

En Ionic, localStorage sirve para el prototipo. Para producción conviene @capacitor/preferences o almacenamiento seguro.

Pendientes del backend

Ordenados por cuánto bloquean al frontend.

  • Bloquea
    Acceso desde otra redEl desarrollador de frontend no alcanza la IP de la red local.Configurar Tailscale (tailscale serve) o Cloudflare Tunnel y agregar el nombre público a ALLOWED_HOSTS.
  • Bloquea
    CORS sin configurarAngular e Ionic no pueden llamar a la API desde el navegador ni desde el WebView.Activar corsheaders con los cinco orígenes de la sección CORS.
  • Bloquea
    No hay endpoints de lecturaGET /api/sensores/, GET /api/mediciones/ (JWT, con filtros recibido_desde y paginación) y GET /api/umbrales/. El GET de mediciones debe exigir JWT sin afectar al POST del ESP32. Agregar el modelo Ubicacion.
  • Bloquea
    Rol en el tokenEnlazar usuario con auth_user y agregar el claim rol con un TokenObtainPairSerializer personalizado.
  • Ajustar
    Expiración a 15 minSIMPLE_JWT = {'ACCESS_TOKEN_LIFETIME': timedelta(minutes=15)}. La inactividad se controla en el frontend.
  • Ajustar
    /auth/me/ es una vista de ejemploDevolver id, username, email, nombre y rol, sin repetir el token.
  • Ajustar
    El enlace de recuperación apunta a la APICambiar PASSWORD_RESET_CONFIRM_URL a la ruta del frontend. Al abrir el enlace actual, el navegador hace un GET y recibe 405.
  • Ajustar
    Decimales como stringOpcional: 'COERCE_DECIMAL_TO_STRING': False en REST_FRAMEWORK. El frontend ya convierte en ambos casos.
  • Ajustar
    Mensajes en inglésLANGUAGE_CODE = 'es' para recibir en español los mensajes de Django y SimpleJWT.
  • Seguridad
    Credenciales en el repositorioSECRET_KEY y la contraseña de MySQL están en settings.py. Moverlas a variables de entorno y cambiar la contraseña de la BD, sobre todo antes de exponer el backend con un túnel.
  • Seguridad
    La ingesta revela qué sensores existenUn código inexistente responde 404 y uno existente con clave incorrecta, 401. Responder 401 en ambos casos y registrar los rechazos en evento_tecnico_ingesta.
  • Orden
    Archivos compilados en git y sin dependencias declaradasAgregar .gitignore para __pycache__ y un requirements.txt.
